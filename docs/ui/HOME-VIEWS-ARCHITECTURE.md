## 2. Утверждённая продуктовая модель

`General Light` и `Kanban` — два альтернативных представления главной страницы врача.
Они не являются двумя независимыми медицинскими программами и не дублируют рабочее
пространство дела.

```text
Главная /dashboard
├── General Light Home
└── Kanban Home
        │
        └── выбор карточки пациента
                ↓
Единый Case Workspace /cases/:id
                ↓
возврат на исходную главную страницу
```

Разделение ответственности:

| Область | Владелец |
|---|---|
| Выбор и обзор дел | `GeneralLightDashboard` или `KanbanDashboard` |
| Переключение вида | `DashboardViewSwitcher` |
| Список доступных видов | `DashboardViewRegistry` |
| Карточка дела | общий `CaseCard` |
| Данные дел | общий `services.cases` |
| Медицинское рабочее пространство | общий маршрут `/cases/:id` и `WorkspacePage` |
| OCR/извлечение текста, документы, анализ, редактор, финализация | только общие модули дела |
| Локальные настройки главной страницы | `appStorage` |

Ключевой инвариант:

> Kanban меняет только способ отображения и личную раскладку дел. Перемещение карточки
> не меняет `CaseStatus`, медицинские данные, документы, заключение или серверную запись.

## 3. Не командный Kanban

Kanban — персональный визуальный органайзер одного врача.

В текущую модель не входят:

- общая командная доска;
- назначение ответственных;
- персональные и общие статусы;
- публикация расположения карточек другим пользователям;
- синхронизация колонок между врачами;
- изменение медицинского статуса дела через drag-and-drop.

Если позднее потребуется совместная доска, это отдельная продуктовая и архитектурная
задача с новым контрактом хранения. Нельзя расширять текущий `placement` до серверного
статуса «по пути».

## 6. Реестр представлений

Фактический контракт:

```ts
type DashboardViewId = 'general-light' | 'kanban'

interface DashboardViewDefinition {
  id: DashboardViewId
  labelKey: 'views.generalLight' | 'views.kanban'
  icon: LucideIcon
}
```

`DASHBOARD_VIEW_REGISTRY` — единственный список вариантов, который читает
`DashboardViewSwitcher`.

Чтобы добавить третье представление:

1. Создать самостоятельный компонент и CSS-модуль.
2. Расширить `DashboardViewId`.
3. Добавить `labelKey` во все три `dashboard.json`.
4. Добавить запись в `DASHBOARD_VIEW_REGISTRY`.
5. Смонтировать панель в `DashboardPage`.
6. Определить ключи сохранения состояния и их версии.
7. Добавить компонентные тесты выбора, сохранения и возврата.
8. Обновить этот документ, `BLOCK-INDEX`, `DEV-LOG` и владение блоком.

Нельзя регистрировать компонент, который обращается к БД напрямую или имеет собственную
копию Case Workspace.

## 7. Монтаж и мгновенное переключение

`DashboardPage` хранит активный вид в React state и записывает его через `appStorage`.
Оба представления остаются смонтированными, а неактивное скрывается атрибутом `hidden`.

Это даёт:

- мгновенное переключение без повторного создания компонентов;
- сохранение React-state фильтров во время переключения на том же `/dashboard`;
- сохранение позиции DOM-прокрутки, пока страница не размонтирована.

Цена текущего решения:

- оба представления запускают свои запросы, даже если одно скрыто;
- General Light выполняет четыре `services.cases.list`, Kanban — ещё один;
- при уходе с `/dashboard` вся страница размонтируется, поэтому неперсистентный state
  теряется.

Оптимизация запросов допустима только после теста, подтверждающего, что переключение и
возврат не теряют состояние. Нельзя условно размонтировать неактивный вид без отдельного
механизма восстановления.

## 8. Данные дел

### 8.1. General Light

Использует четыре независимых запроса с сортировкой `updatedAt desc`, `limit: 100`:

| Секция | Статусы |
|---|---|
| Продолжить работу | `draft`, `documents_uploaded`, `phi_review`, `processing`, `analyzing`, `error` |
| Требует внимания | `needs_attention` |
| Готово к проверке | `ready_for_review` |
| Недавно завершено | `finalized` |

Существующая логика General Light не должна изменяться при работе над Kanban.

### 8.2. Kanban

Один запрос:

```ts
services.cases.list({
  statuses: ALL_STATUSES,
  sort: 'updatedAt',
  dir: 'desc',
  limit: 100,
  offset: 0,
})
```

Текущий `ALL_STATUSES` не включает `archived`.

`CaseService.list` остаётся tenant-scoped. Компонент не получает репозиторий или БД и не
имеет права обходить сервисный слой.

### 8.3. Query keys

- General Light: `['cases', 'dashboard', key, statuses]`;
- Kanban: `['cases', 'dashboard', 'kanban']`.

После создания, удаления или изменения дела общая логика мутаций должна инвалидировать
семейство `['cases']`, чтобы оба вида получили актуальные данные.

## 9. Текущая модель Kanban

```ts
interface KanbanColumn {
  id: string
  title: string
  color: string
}

interface KanbanLayout {
  columns: KanbanColumn[]
  placement: Record<string, string> // caseId -> columnId
}
```

`placement` — только визуальная личная раскладка. Он не равен `CaseStatus`.

Начальное отображение дела без явного `placement` вычисляется из статуса:

| Статус | Стартовая колонка |
|---|---|
| `draft`, `documents_uploaded` | `incoming` |
| `needs_attention`, `error` | `attention` |
| `ready_for_review` | `review` |
| `finalized` | `done` |
| `phi_review`, `processing`, `analyzing` | `working` |

`archived` сейчас не загружается Kanban.

## 10. Операции с колонками

Поддерживаются:

- добавление колонки;
- произвольное непустое название;
- выбор RGB-цвета через `<input type="color">`;
- переименование и изменение цвета;
- изменение порядка кнопками «раньше/позже»;
- удаление колонки при наличии хотя бы одной другой;
- выбор целевой колонки для переноса карточек;
- сохранение порядка колонок.

Обязательные инварианты:

1. Должна существовать минимум одна колонка.
2. `id` колонки стабилен после создания.
3. Название не участвует в логике и может повторяться.
4. Цвет влияет только на оформление.
5. Удаление колонки не удаляет дела и не меняет медицинские данные.
6. Все дела из удаляемой колонки должны оказаться в выбранной целевой колонке.
7. После любой операции layout должен оставаться валидным и сериализуемым.

## 11. Перетаскивание карточек

Текущая реализация использует HTML5 Drag and Drop:

- MIME: `application/x-daatmed-case`;
- payload: только `CaseSummary.id`;
- drop вызывает `moveCase(caseId, columnId)`;
- обновляется только `layout.placement`;
- сервис дел не вызывается.

Запрещено помещать в drag payload имя пациента, номер дела или иные PHI.

Нужно учитывать, что HTML5 DnD без альтернативы не обеспечивает полноценное управление
с сенсорного экрана и клавиатуры. Добавление доступного меню «Переместить в…» должно
переиспользовать `moveCase`, а не создавать второй путь изменения состояния.

## 12. Фильтрация и годы

Поиск выполняется локально по уже загруженным `CaseSummary`:

- `patientLabel`;
- `caseNumber`;
- регистр игнорируется;
- поиск не отправляется отдельным запросом.

Год вычисляется так:

1. первое совпадение `20xx` в `caseNumber`;
2. иначе первые четыре символа `createdAt`.

Фильтр года и поиск влияют только на видимость карточек, не на layout и не на данные дела.
Счётчики колонок считаются по отфильтрованному набору.

## 13. Открытие дела и возврат

`CaseCard` — общий `<Link to="/cases/:id">`. Маршрут `/cases/:id` открывает единый
`WorkspacePage` вне глобального `AppShell`.

Текущий `WorkspaceTopBar` возвращает кнопкой Home на `/dashboard`. Выбранный вид
восстанавливается из `dashboard.active-view.v1`, поэтому открытое из Kanban дело
возвращает пользователя в Kanban.

Утверждённый критерий полного возврата из Kanban:

- тот же активный вид;
- тот же выбранный год;
- тот же поисковый запрос;
- тот же layout колонок;
- те же placements;
- та же горизонтальная позиция доски;
- без изменения данных дела.

`query` и `year` сериализуются отдельно от layout в
`dashboard.kanban.view-state.v1`. Поэтому размонтирование dashboard при переходе в
`/cases/:id` не сбрасывает временное состояние, а возврат через Home восстанавливает
активный вид, поиск, год, раскладку и горизонтальную прокрутку.

## 14. Хранение состояния

Весь доступ выполняется только через `appStorage`.

| Ключ | Значение | Текущая версия |
|---|---|---|
| `dashboard.active-view.v1` | `'general-light'` или `'kanban'` | v1 |
| `dashboard.kanban.layout.v2` | JSON `KanbanLayout` | v2 |
| `dashboard.kanban.layout.v1` | прежний layout, только источник миграции | legacy |
| `dashboard.kanban.view-state.v1` | JSON `{ query, year }` | v1 |
| `dashboard.kanban.scroll.v1` | строковое число `scrollLeft` | v1 |

В браузере `appStorage` делегирует `window.localStorage`. В Electron он работает через
прогретый snapshot и write-through в локальное SQLite-хранилище. Компоненты не должны
знать реализацию адаптера.

Пример текущего layout:

```json
{
  "columns": [
    { "id": "incoming", "title": null, "color": "#66889a" },
    { "id": "working", "title": "Сделать сегодня", "color": "#b47a38" }
  ],
  "placement": {
    "case-123": "working"
  },
  "statusPlacement": {
    "draft": "working"
  }
}
```

`title: null` означает встроенное локализованное название. Строка означает
пользовательское название и никогда не переводится. `statusPlacement` сохраняет
назначенную пользователем колонку для статуса после удаления встроенной колонки, в том
числе для ещё не загруженных дел.

### 14.1. Правила изменения схемы

Нельзя менять значение существующего `*.v1` несовместимым образом.

Для несовместимой схемы:

1. создать новый ключ `*.v2`;
2. описать zod-схему или равноценную строгую валидацию;
3. сделать детерминированную миграцию v1 → v2;
4. при ошибке миграции сохранить старое значение и безопасно открыть дефолт;
5. добавить unit-тесты валидного, повреждённого и частично устаревшего значения;
6. после успешной записи v2 старый ключ можно оставить на один релиз для отката.

Нельзя молча очищать пользовательскую раскладку при неизвестном поле или временной ошибке.

## 15. i18n, RTL и BiDi

Видимые системные строки находятся в namespace `dashboard` и должны существовать в
`ru`, `he`, `en`.

Обязательные правила:

- новые ключи добавляются симметрично во все три файла;
- CSS использует logical properties (`inline`, `block`, `margin-inline-*`,
  `border-inline-*`);
- иконки порядка колонок должны отражать логическое «раньше/позже», а не жёсткое
  «влево/вправо»;
- `patientLabel` выводится через `<bdi>`;
- `caseNumber` находится в `.bidi-isolate`;
- пользовательские названия колонок показываются в текущем направлении интерфейса,
  без изменения сохранённой строки;
- дефолтные названия колонок должны создаваться из локализованного источника или
  языка-независимых ID, а не быть зашиты на одном языке.

## 16. Состояния UI

### General Light

Каждая секция независимо поддерживает:

- loading — skeleton;
- error — critical alert + retry;
- empty — `EmptyState`;
- ready — карточки и сворачивание.

### Kanban

- loading — три skeleton;
- error — critical alert + retry;
- empty после фильтра — `EmptyState`;
- пустая колонка — drop-zone с подсказкой;
- editor open — modal dialog;
- повреждённый layout — безопасный fallback на default layout.

Ошибка чтения layout не должна мешать загрузке дел. Ошибка загрузки дел не должна
стирать layout.

## 17. Доступность

Уже предусмотрено:

- `SegmentedControl` с `aria-label`;
- заголовок Kanban;
- `aria-label` у списка годов;
- подписанные кнопки порядка и настройки колонок;
- `role="dialog"` и `aria-modal="true"`;
- текстовые счётчики, не только цвет;
- disabled-состояния крайних кнопок порядка.

Обязательные доработки при следующей итерации:

- focus trap и возврат фокуса для редактора колонки;
- закрытие диалога по Escape;
- доступное имя для полей через корректную связь `label`/control;
- клавиатурное/сенсорное «Переместить в…» для карточки;
- объявление результата перемещения через `aria-live`;
- тест порядка фокуса и RTL.

## 18. Известные расхождения и риски ветки

### 18.1. Исправленные расхождения

1. Удаление любой колонки переносит явные и неявные карточки в выбранную колонку.
   `statusPlacement` обеспечивает тот же результат для ещё не загруженных карточек.
2. Поиск и год восстанавливаются после возврата из Workspace.
3. Встроенные названия колонок берутся из i18n RU/HE/EN; пользовательские названия
   сохраняются буквально.
4. Layout v1 мигрирует в строго проверяемый v2; исходный v1 при ошибке не удаляется.
5. Kanban использует постраничный `useInfiniteQuery`: первые 100 дел не являются
   скрытым пределом, а кнопка «Загрузить ещё» добавляет следующую страницу.
6. `archived` включён в выборку и по умолчанию попадает в колонку `done`.

### 18.2. Проверочный статус

Добавлены unit/component-регрессии перечисленных исправлений. Полный
`typecheck + lint + vitest + build + block-index` обязан пройти в CI ветки до слияния.

### 18.3. Требуют отдельной задачи

1. **Хранилище не namespaced по пользователю/tenant.** На общем компьютере настройки
   потенциально общие для профиля приложения. Нужен согласованный ключевой namespace.
2. **Оба скрытых/видимых dashboard запрашивают данные одновременно.** Решить, приемлема

## 20. Тестовая матрица

### 20.1. Registry и переключатель

- `[unit]` реестр содержит уникальные ID и существующие i18n keys во всех языках;
- `[component]` default без storage = General Light;
- `[component]` неизвестное значение storage = General Light;
- `[component]` выбор Kanban виден сразу и сохраняется;
- `[component]` переключение туда/обратно не сбрасывает `query`, `year` и layout;
- `[component]` RU/HE/EN имеют доступные имена вкладок.

### 20.2. Layout

- `[unit]` отсутствие storage создаёт default layout;
- `[unit]` повреждённый JSON не падает и не перезаписывает данные до безопасной записи;
- `[unit]` пустой/невалидный columns даёт fallback;
- `[unit]` duplicate column IDs отклоняются;
- `[unit]` неизвестный placement получает безопасную колонку;
- `[unit]` новая колонка сохраняет title/color/order;
- `[unit]` переименование не меняет ID;
- `[unit]` удаление любой, включая дефолтную, переносит явные и неявные карточки;
- `[unit]` последнюю колонку удалить нельзя.

### 20.3. Карточки

- `[component]` карточка находится в колонке по статусу без placement;
- `[component]` placement имеет приоритет над status mapping;
- `[component]` drop меняет только placement и не вызывает мутацию `CaseService`;
- `[component]` поиск работает по пациенту и номеру дела;
- `[component]` фильтр года не изменяет placement;
- `[component]` `archived` отображается в `done`, если нет персонального placement;
- `[component]` кнопка загрузки следующей страницы добавляет 101-е дело и сохраняет
  первые 100.

### 20.4. Навигация

- `[e2e]` General Light → дело → Home = General Light;
- `[e2e]` Kanban → дело → Home = Kanban;
- `[e2e]` Kanban → дело → Home восстанавливает query/year/layout/scroll;
- `[e2e]` прямой вход `/cases/:id` → Home использует сохранённый preferred view;
- `[e2e]` изменение дела в Workspace после возврата видно в обоих представлениях.

### 20.5. RTL и доступность

- `[component]` `document.dir=rtl`: years и board зеркальны через logical CSS;
- `[component]` порядок колонок «раньше/позже» семантически корректен в RTL;
- `[component]` mixed Hebrew + case number не меняет порядок символов;
- `[component]` диалог удерживает и возвращает фокус, закрывается по Escape;
- `[component]` карточку можно переместить без мыши;
- `[manual]` светлая/тёмная тема, 1024/1280/1600 px и ≤760 px.

## 23. Критерии приёмки интерфейса

Функция может считаться готовой к слиянию, когда одновременно выполнено следующее:

- General Light работает без регрессий;
- переключение происходит без перезагрузки;
- выбор вида сохраняется;
- Kanban остаётся персональным и не меняет CaseStatus;
- любая колонка создаётся, переименовывается, перекрашивается, переставляется и безопасно
  удаляется;
- ни одна карточка не исчезает после настройки колонок;
- открытие карточки ведёт в общий `/cases/:id`;
- возврат восстанавливает весь утверждённый state;
- дефолтные названия корректны в RU/HE/EN;
- принято явное решение по `archived`, пагинации и user namespace;
- основной поток доступен с клавиатуры и не ломается на touch;
- RTL/BiDi проверены;
- полный рецепт §21 зелёный;
- documentation/DEV-LOG/ownership синхронизированы;
- ветка не конфликтует с актуальным `main`.

До выполнения этих пунктов корректный статус ветки:

> Реализация исправлена по известным расхождениям. До слияния требуется зелёный полный
> CI и отдельное решение по user/tenant namespace и доступному перемещению карточек на
> touch/keyboard.
